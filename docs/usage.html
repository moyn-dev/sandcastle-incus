1. Environment setup

Build binaries

Build native binaries for local use, or cross-compile for handoff to other hosts. Each cross target writes bin/<os>-<arch>/{sandcastle,sc,sandcastle-admin,sc-adm}.

mise run build
mise run build:linux-amd64    # Linux x86-64
mise run build:linux-arm64    # Linux arm64
mise run build:darwin-arm64   # macOS Apple Silicon
mise run build:all           # all three of the above

Install the user CLI

From a release (Linux and macOS). The install script picks the right sandcastle-<os>-<arch>.tar.gz for your machine, verifies its SHA-256 against the release's checksums.txt, and installs the binary as sandcastle in ~/.local/bin with an sc symlink beside it:

curl -fsSL https://raw.githubusercontent.com/thieso2/sandcastle-incus/main/install.sh | bash
sc version

Flags go after -s -- when piping (| bash -s -- --version v0.8.0): --version <tag> installs (or rolls back to) a specific release, --dir <path> installs elsewhere, and --admin also links sc-adm / sandcastle-admin for operators. Each has an env-var form (SANDCASTLE_VERSION, SANDCASTLE_INSTALL_DIR, SANDCASTLE_ADMIN=1). The script only writes inside the install directory — it never edits your shell profile; when the directory is not on PATH it prints the line to add. Because the binary then lives in a directory you own, sc update can self-replace it, which a Homebrew install deliberately cannot. Re-running the script is the other way to upgrade.

Homebrew (macOS). brew install thieso2/tap/sandcastle, upgraded with brew upgrade sandcastle. Casks are macOS-only.

From a source checkout. mise run install installs the binary you just built into ~/.local/bin when that directory is already on PATH; otherwise into /usr/local/bin.

mise run install
sc version

Normal tenant users do not need sandcastle-admin or sc-adm; those are operator tools for tenant, infrastructure, image, and sidecar administration.

Keep the CLI and your sidecar updated (sc update) user

The CLI checks GitHub for a newer release at most once per 24h in the background of normal commands and prints a two-line notice on stderr when one is available (suppressed for dev builds, non-TTY runs, releases younger than 24h, and when SANDCASTLE_NO_UPDATE_NOTIFIER is set). Updates are always user-initiated — never automatic.

sc update --check            # status table: CLI, sidecar, skills, and each project's shared /.sc payload
sc update                    # show the table, then prompt to apply what's outdated
sc update --yes              # apply without prompting
sc update --version v0.18.2  # pin (or roll back to) a release

Cache first. Every sc command that starts by reading the tenant's projects (nearly all of them) and the payload check of sc update ask the Auth App's event-fed resource cache first: one HTTPS request instead of a live GET /1.0/projects plus per-project reads against Incus. Any non-answer (not logged in, cache not ready, timeout) falls back to the live path unchanged; VERBOSE=1 shows the fallback reason, and SANDCASTLE_CONNECT_CACHE=0 disables the cache client-side. The appliance must run v0.18.26 or newer to serve projects and payload versions.

One run does everything: when the CLI itself was outdated, sc update replaces the binary and then re-runs itself with the new one to apply the remaining stages (sidecar, agent skills, project payloads), since the skill and the payload are embedded in the executable. Each stage prints what it changes (== sc CLI: v0.18.12 -> v0.18.14, per-project payload versions, …). The status table details only what is outdated; everything current is folded into one summary line per kind (platform payloads … 22 project(s) current). Asset downloads get their own 15-minute deadline, so a slow link no longer fails with context deadline exceeded after 30 s.

Release lookups do not use the GitHub API and need no token: the CLI reads the tag from the github.com/…/releases/latest redirect and downloads the fixed GoReleaser assets from releases/download/<tag>/, verified against checksums.txt. Anonymous API calls share one small rate limit per public IP address, which behind a NAT produced API rate limit exceeded notes; the API is now only the fallback, and it is authenticated automatically when GITHUB_TOKEN or GH_TOKEN happens to be set.


sc update --version v0.3.1   # pin the CLI to a tag (an older tag rolls back)

Copies of the agent skill that sc skill install wrote appear in the table as skill (claude, user) / skill (codex, user) rows and are refreshed (non-fatally, one line per copy) when outdated.

The CLI target downloads sandcastle-<os>-<arch>.tar.gz from the release, verifies its SHA-256 against checksums.txt, and atomically replaces the binary, keeping the previous one as .bak. Homebrew-managed installs are never self-replaced — the command prints brew upgrade sandcastle instead; an install from install.sh (or any writable directory) self-replaces in place on both Linux and macOS. The sidecar target is delegated to the deployment (auth-app token plane, broker mTLS fallback), which pushes its own running binary into your sidecar and restarts only the TLS leaf signer (sub-second; DNS and connectivity untouched). A platform payload row is one centrally-managed /.sc volume per visible project: updating it reaches every Machine in that project without an SSH sweep. If the CLI itself was replaced, run sc update once more to write the payload bundled in that new executable; the old running process never writes an old payload under a new version label.

Agent skill for Claude Code and Codex (sc skill) user

The Sandcastle agent skill (the SKILL.md + reference files that teach a coding agent how to drive sc/sc-adm, tracked at docs/agents/skills/sandcastle/) ships inside the binary. Install it once per machine; sc update refreshes copies it installed.

sc skill install                          # Claude Code + Codex, user scope; skips an agent whose config dir is absent
sc skill install --agent codex            # one agent; an explicitly named agent gets its dir created
sc skill install --scope project          # into the current git repo: .claude/skills/ and .agents/skills/
sc skill install --dir ./skills           # explicit directory (lands at ./skills/sandcastle); ignores --agent/--scope
sc skill install --force                  # replace a hand-placed copy (a directory without the sc marker)
sc skill status [--json]                  # AGENT SCOPE PATH STATE: missing | up to date | outdated (v… → v…) | unmanaged
sc skill uninstall                        # removes only copies sc installed; --dry-run on install/uninstall
sc skill show                             # print the embedded SKILL.md (pipe it wherever)

Locations: Claude Code reads $CLAUDE_CONFIG_DIR/skills/sandcastle (default ~/.claude/skills/sandcastle) and <repo>/.claude/skills/sandcastle; Codex reads $CODEX_HOME/skills/sandcastle (default ~/.codex/skills/sandcastle) and the repository skill root <repo>/.agents/skills/sandcastle. Every install is written atomically (staged next to the target, then renamed in) and carries a .sc-skill-version marker with the skill content version and the CLI version that wrote it. Without the marker a directory is unmanaged: install refuses it unless --force, uninstall and sc update leave it alone.

Reminder. When an interactive sc command succeeds (stdout and stderr both terminals, no --json/--output json), the CLI checks the user-scope copies for the agents present on the box (~/.claude → Claude Code, ~/.codex or $CODEX_HOME → Codex) and, if one is missing or outdated, prints one line on stderr after the command's output, at most once per 24h (throttle file ~/.config/sandcastle/skill-reminder-state.json, next to the update notice's):

hint: the Sandcastle agent skill is not installed for Claude Code and Codex — run: sc skill install   (silence: sc config set skill-reminder off)

It is a local filesystem check only (no network), never printed by sc-adm, sc admin …, sc skill … itself, or on a failed command. sc skill install resets the throttle. Silence it for good with sc config set skill-reminder off (on or sc config unset skill-reminder re-enables) or for one shell with SANDCASTLE_SKILL_REMINDER=0.

Config file (recommended)

Store your defaults in ~/.config/sandcastle/config.yml so you don't need to set env vars on every call.

# ~/.config/sandcastle/config.yml
tenant: acme
project: website
remote: sc-alice

Once set, sc create codex works without any extra flags or exports.

Environment variables take precedence over the config file if both are set.

sc config set project website
sc config unset project
sc config set skill-reminder off   # silence the daily agent-skill hint (on / unset re-enables)
sc config show

sc login now records the tenant's project into project: for you, so you rarely set it by hand — see Initial & current project.

sc info prints the active context (tenant, project, remote, auth hostname) and the projects available in the current tenant, marking the current one with *. It fetches the project list live but degrades to the local config (with a note) when the tenant can't be reached, and it never fails on a connectivity error. Use it to discover valid project names for [[project:]machine] references.

sc info
# Tenant:   acme
# Project:  website
# Remote:   sc-alice
# Auth:     auth.example.com
#
# Projects in acme:
#   * website
#     backend

Admin environment variables

Set these before running any sandcastle-admin command, or put them in a local .env file in the current directory. Exported environment variables override .env, and both override the config file for admin commands. For sc-adm install, CLI flags override environment variables, environment variables override the infrastructure seed file, and the seed overrides built-in defaults. Normal sandcastle (sc) user commands ignore local .env files and read only the saved Sandcastle config plus explicitly exported environment variables.

# Incus remote name (default: local)
export SANDCASTLE_REMOTE=big

# Storage pool name in Incus
export SANDCASTLE_STORAGE_POOL=default

# Private CIDR pool for tenant networks (optional; default 10.248.0.0/16)
export SANDCASTLE_CIDR_POOL=10.248.0.0/16

# Prefix for managed tenant Incus projects (optional; default sc)
export SANDCASTLE_INCUS_PROJECT_PREFIX=sc

# Infrastructure Incus project name (shared Caddy / appliances)
export SANDCASTLE_INFRA_PROJECT=sc-infra

# Optional public Auth App hostname reserved by shared Caddy
export SANDCASTLE_AUTH_HOSTNAME=auth.example.com

# GitHub OAuth app credentials for Auth App login
export SANDCASTLE_AUTH_GITHUB_CLIENT_ID=...
export SANDCASTLE_AUTH_GITHUB_CLIENT_SECRET=...

# Initial Sandcastle Admin GitHub usernames, comma-separated
export SANDCASTLE_AUTH_ADMIN_GITHUB_USERS=octocat,hubot

# Optional lab-only device approval bypass user
export SANDCASTLE_AUTH_DEBUG_DEVICE_USER=octocat

# Optional lab/unattended Tailscale sidecar attachment key returned by Device Login
export SANDCASTLE_AUTH_TAILSCALE_AUTHKEY=tskey-auth-...

# Host Incus socket mounted for Auth App provisioning and the broker sidecar (default shown)
export SANDCASTLE_ROUTE_BROKER_INCUS_SOCKET=/var/lib/incus/unix.socket

# Optional prebuilt Linux admin binary uploaded into infrastructure sidecars
export SANDCASTLE_ADMIN_BIN=$PWD/bin/linux-amd64/sc-adm

# Let's Encrypt email for shared Caddy TLS
export SANDCASTLE_LETSENCRYPT_EMAIL=ops@example.com

# Optional exported Caddy ACME data archive restored during install
export SANDCASTLE_INFRA_CADDY_DATA_ARCHIVE=~/.config/sandcastle/infra-caddy-data/big/sc-infra/caddy-data.tgz

# Debug TLS mode: use Caddy's internal CA instead of public ACME
export SANDCASTLE_INFRA_TLS_MODE=internal

Incus certificate selection and admin_remote

sandcastle-admin (sc-adm) always uses the global Incus config (~/.config/incus/) which holds admin certificates. sandcastle (sc) user commands use the per-remote Sandcastle config directory (~/.config/sandcastle/<remote>/incus/) which holds the restricted user certificate. Local repo .env defaults are intentionally admin-only so they cannot redirect sc to the admin remote.

The admin remote is the Incus remote name as it appears in ~/.config/incus/config.yml (e.g. big). It may differ from the Sandcastle user remote (e.g. sc-alice). Configure it once with:

sc-adm config set admin_remote big
# or
export SANDCASTLE_ADMIN_REMOTE=big

When admin_remote is set, sc-adm uses it instead of remote. When unset, sc-adm auto-detects the admin remote by comparing server TLS certificates between the global and per-remote Incus configs.

2. Create & manage tenants admin

List tenants

sandcastle-admin tenant list
sandcastle-admin tenant list --json  # JSON output

# Show all resources (metadata + machines across all projects) for a specific tenant
sandcastle-admin tenant list acme

Create a tenant

Provisions a tenant Incus project with private bridge network, storage volumes, Tailscale sidecar, CoreDNS sidecar, and tenant-local Sandcastle image aliases.

sandcastle-admin tenant create acme
Note: Machine hostnames are <machine>.<project>.<suffix> where the Tenant DNS Suffix defaults to the tenant name (e.g. codex.default.acme) and can be chosen at creation with --dns-suffix (single label, immutable; also available on sc login for first-login provisioning). Machines in the default project additionally answer at the short alias <machine>.<suffix>; machines in other projects have no short name (ADR-0018). Under ADR-0021 the suffix is also the incus remote name — <suffix> alone, one remote per install (not per project); the project is selected locally by sc project switch. The suffix is unique per install — a first login reserves it, and a second tenant choosing a taken suffix on the same install is rejected.
# Preview what will be created without mutating anything
sandcastle-admin tenant create acme --dry-run

Create a v2 tenant admin v2 MVP

The v2 MVP (see docs/adr/0016-v2-mvp-admin-provisioned-native-incus.md) provisions a tenant for native incus access: one per-tenant infra project sc2-<tenant> with a single sidecar (CoreDNS + Tailscale subnet-router), a shared bridge, and a seeded default app project sc2-<tenant>-default whose profile carries the shared bridge NIC + cloud-init login. Machines resolve at <machine>.<project>.<suffix>, with a short <machine>.<suffix> alias for the default project only (see docs/adr/0018-machine-private-hostnames.md). Prints a restricted Incus certificate-add token the tenant redeems with their own client.

sandcastle-admin tenant create acme --tailscale-authkey tskey-… --ssh-key "ssh-ed25519 AAAA…"
# --cidr-pool defaults to 10.249.0.0/16; --sidecar-image
# takes a system-container base image (alias/fingerprint); --dry-run to preview
No auth key? Omit --tailscale-authkey and the sidecar starts tailscale up interactively; the command prints a https://login.tailscale.com/a/… URL to open and approve, registering the sidecar into your own tailnet. Re-running create after registration is a no-op for Tailscale.
Native use: after incus remote add … --token=…, the tenant runs plain incus launch images:debian/13/cloud web into sc2-acme-default and reaches it at web.default.acme (short alias web.acme — default project only). Cloud-init images are required for login. Add more projects with sandcastle-admin project create acme backend (admin) or, tenant self-service, sc project create backend (after sc login no flags are needed: the request rides the Auth App's token-gated POST /api/projects over the public hostname — tunnel-friendly, no broker port, no client certificate; pass --broker to use the client-cert broker path instead). Under ADR-0021 sc project create does not add a separate per-project remote by default — your install's single <suffix> remote plus sc project switch <name> reaches every project (the switch writes the nearest .sandcastle). Pass --write-remote to also drop an extra directly-addressable <tenant>-<project>: remote. End-to-end coverage: scripts/e2e-v2.sh.

Set or update tenant SSH key

Agentic toolchain. Every machine has install-agentic.sh on its PATH (from the shared /.sc/platform/bin): run it as your login user and it installs mise into ~/.local/bin, then herdr, claude (Claude Code) and codex through mise; re-run it to upgrade. The shared shell rc keeps ~/.local/bin and the mise shims on PATH (so ssh <machine> claude works non-interactively) and activates mise in interactive shells. SC_AGENTIC_TOOLS narrows the tool set. Machines created earlier get the script with the next payload sync.

The shell prompt on every machine is user@<fqdn>:<dir>$, and just <fqdn>:<dir>$ when the login user is the tenant itself (the default), so a terminal always says which machine it is on. It is applied by the shared /.sc shell rc at the first prompt, replacing only the stock Debian prompt; a prompt you set yourself in ~/.bashrc is left alone.

The login user baked into a tenant's machines defaults to the tenant name (a shared tenant moyn-dev logs in as moyn-dev); tenant create --unix-user <name> chooses another, a login keeps the client's local user, and a stored user is never changed by a re-run. Only a tenant name that is not a valid Unix username falls back to dev.

The user publishes her own SSH public key at login time with sc login --ssh-public-key <path>; the key is baked into the tenant's default-project profile and injected into machines created afterwards. A tenant holds a list of keys (one per line in its metadata): the first is the tenant's own login key, further ones are added by an operator. tenant create --ssh-key is repeatable; set-ssh-key replaces the whole list, add-ssh-key appends, remove-ssh-key drops one key (matched on the key material, not its comment; the last key cannot be removed). Every change re-renders the tenant's profiles; running machines keep their keys until sc fix --only ssh-key enrols the new one.

sandcastle-admin tenant set-ssh-key acme "ssh-ed25519 AAAA..."
sandcastle-admin tenant add-ssh-key acme "ssh-ed25519 BBBB... laptop"
sandcastle-admin tenant remove-ssh-key acme "ssh-ed25519 BBBB..."

Create a Shared Tenant

A Shared Tenant is a tenant several users manage together (ADR-0029). Its Tenant Members are recorded in the tenant's metadata, every member's login SSH key is authorized on its machines (read from the member's Personal Tenant, so it follows the member's key rotation at login), and each member's restricted certificate covers every project of the tenant. Prerequisite: every member has already completed sc login on this install and is on the tenant's tailnet; a member who never logged in is refused.

sandcastle-admin tenant create moyn-dev --member thieso2 --member skorfmann --tailscale-authkey tskey-… --dns-suffix moyn
sandcastle-admin tenant grant moyn-dev alice     # add a member later: certificate scope, membership, profiles, running machines
sandcastle-admin tenant revoke moyn-dev alice
sandcastle-admin tenant users moyn-dev

--cidr-pool may be omitted: the tenant's /24 comes from the configured pool (SANDCASTLE_CIDR_POOL / seed), else from the /16 the install's existing tenants already occupy, and only on an empty install from the built-in 10.249.0.0/16. Without --tailscale-authkey the command prints the sidecar's interactive login.tailscale.com URL.

Members then run sc tenant switch moyn-dev (see Select an accessible tenant): the CLI enrols an Incus remote named after the tenant's DNS suffix at the tenant sidecar's tailnet address, pins its default project, and every sc command — including sc project create, hostnames, certificates and shares through the Auth App — acts on the shared tenant until they switch back. The Auth App's /admin/access page performs the same grant and revoke.

SSH host keys — automatic, authoritative, self-healing

You do not manage host keys. On every sandcastle connect (v2), the CLI reads the machine's SSH host keys over the Incus API — never from the network — and records them in ~/.ssh/known_hosts under the Machine Private Hostname, then connects with StrictHostKeyChecking=yes. Rebuilding a machine changes its host key; the entry is reclaimed automatically, so you never see REMOTE HOST IDENTIFICATION HAS CHANGED. A plain ssh <machine>.<project>.<suffix> uses the same entries and just works.

# every line Sandcastle writes is marked, so it can be reclaimed and purged safely
tubu.default.acme,tubu.acme ssh-ed25519 AAAA... # sandcastle:<remote>/<tenant>

sandcastle ssh-key purge --dry-run   # report what is stale, change nothing
sandcastle ssh-key purge             # drop entries for deleted machines + recycled private IPs
sandcastle ssh-key purge --all --yes # every v2 tenant, no confirmation
What purge will and will not delete. It removes only lines Sandcastle wrote (marked # sandcastle:<remote>/<tenant>) plus untagged literal IP addresses inside the tenant's own private CIDR — recycled DHCP leases with no lasting owner. Your own entries, @cert-authority/@revoked lines, and other hosts are never touched; a wildcard of yours that would shadow a machine name is reported, not removed. The first destructive change each day snapshots the file to ~/.ssh/known_hosts.sc-backup-<date>, and every removal is printed.
Virtual machines. Reading a VM's host key needs incus-agent running inside the guest. When it is not, connect falls back to ssh-keyscan, warns, and marks the entry tofu (trust on first use). Any later connect that can read the machine rewrites the entry and drops the marker. See docs/adr/0020-authoritative-ssh-host-keys.md.

Tenant status

sandcastle-admin tenant status acme

Delete a tenant (keep volumes)

Stops the tenant's runtime resources (sidecar, network) but preserves the durable home/workspace volumes and the Incus projects. Re-run with --purge to destroy everything.

sandcastle-admin tenant delete acme --yes

Sync the /.sc platform payload

Converges every app project of a tenant onto the /.sc/platform scripts payload built into this binary (ADR-0022) — one shared-volume write per project, never per machine. Every running machine observes the new payload through its /.sc mount; the baked shims pick it up on next use, no re-create needed. Projects provisioned before /.sc are onboarded in the same pass: the sync creates the missing sc-platform/sc-local volumes and additively merges their disk devices into the default profile (running machines pick the mounts up live). --check reports each project's payload version against the binary's (drift detection) without changing anything; rolling back = running payload-sync from the previous binary.

sandcastle-admin tenant payload-sync acme
sandcastle-admin tenant payload-sync acme --check

Purge a tenant (destroy everything)

Removes every app project (machines, images, shared home/workspace volumes, profiles), the infra project (sidecar), and the tenant bridge — scoped to the installation prefix (SANDCASTLE_INCUS_PROJECT_PREFIX), so a same-named tenant of another install on the same daemon is untouched. The sidecar's tailnet device is the tenant's own (BYO tailnet) — remove it in the Tailscale admin console, or use ephemeral keys.

sandcastle-admin tenant delete acme --yes --purge

3. Create users & credentials admin

Create a restricted user certificate

Issues a restricted certificate add-token for alice. Use --tenant to embed tenant access in the token so the user can onboard asynchronously.

sandcastle-admin user create alice --tenant acme

Example output:

User: alice
Certificate: sc-alice
Remote: sc-alice
Token: 7f3a...
Bootstrap:
  sc remote add sc-alice <join-token> --tenant acme
Share the bootstrap command with the user. They run sc remote add on their machine — this registers the remote, saves it as the default in ~/.config/sandcastle/config.yml, and applies the tenant grant embedded in the token.

Grant a user access to a tenant

Tenant access is managed with the tenant commands. A grant adds the tenant's infra project and every app project to the user's certificate restriction list and, on a v2 tenant, records the user as a Tenant Member (Shared Tenants above). The certificate addressed is the one the user's login enrolled on this install (sandcastle-<prefix>-<user> on a --prefix install).

sandcastle-admin tenant grant acme alice
sandcastle-admin tenant revoke acme alice
sandcastle-admin tenant users acme

Issue a new add-token for an existing user

Use this if the user lost their token or you need to re-register the remote. Include --tenant when the replacement token should be pre-granted.

sandcastle-admin user token alice --tenant acme

Delete a restricted user certificate

Removes the user's restricted Incus certificate entirely. This revokes all tenant access for that certificate. Prompts for confirmation when run interactively; use --yes for scripts.

sandcastle-admin user delete alice --yes

CLI Device Login

Starts browser-assisted sign-in against the Auth App. The CLI prints a verification URL and user code, then polls until the browser approval completes, expires, or is denied.

sandcastle login https://auth.example.com
sandcastle login --dns-suffix acme  # deprecated: the suffix defaults to the tenant name; public names come from Project Domains https://auth.example.com   # first login: choose the Tenant DNS Suffix
sandcastle login --default-project web https://auth.example.com   # first login: name your initial project (replaces "default")
Tenant DNS Suffix & remote name (ADR-0020/0021): at first login the tenant's DNS Suffix (default = tenant name) is reserved on the install and becomes the enrolled incus remote's name — <suffix> alone, one remote per install (ADR-0021), pinned to your initial project; it is immutable, so re-login returns the stored suffix and needs no flag. You can set the suffix two ways: type it into the DNS suffix field on the browser device-approval page, or pass --dns-suffix on the CLI — when both are given, the CLI flag wins. A suffix already claimed by another tenant on that install is rejected. On re-login, the tenant's legacy / per-project remotes for this install are lazily collapsed to the single <suffix> remote (endpoint-scoped; the current remote is never removed).
Initial project name (issue #93): at first login you may also name your tenant's one project instead of the default default. It becomes the middle part of machine hostnames (<machine>.<project>.<suffix>), the project the install's single <suffix> remote is initially pinned to, and the holder of the DNS short-alias. Set it two ways — the Initial project field on the browser device-approval page or --default-project (alias --initial-project) on the CLI, CLI wins. Unlike the suffix it is not immutable; blank ⇒ default, and re-login reuses the stored name.
Current project stored on login: after a successful login sc writes the tenant's project into ~/.config/sandcastle/config.yml (project:) so bare machine references — sc c <machine>, sc create <machine> — resolve without --project or a manual sc config set project. If the tenant has a single project it is stored silently; if it has several, an already-valid configured choice is kept, otherwise you are prompted to pick one (a non-interactive login defaults to the tenant's current project and prints a note). Passing --default-project selects it directly without a prompt. Inspect the result with sc info.
Approval page adapts to your tenant: the browser device-approval page only shows the DNS suffix and Initial project inputs on your first login, when there is nothing to name yet. Once your tenant exists, the page instead displays your existing (immutable) DNS suffix and current projects read-only — there is nothing to fill in, so re-approving is a single click. The CLI flags (--dns-suffix, --default-project) behave the same regardless.

Idempotent (no browser when already authorized). Before starting a device flow, login checks whether you already hold a working login for the requested Auth Hostname — the saved CLI Auth Token is still accepted by the Auth App, the enrolled Incus remote responds, and the tenant subnet is reachable over the tailnet. If so it reports Already logged in and exits, no web. Crucially this is resolved from the per-install credential maps (installs / auth_tokens in your config), not just the currently-active install: running sc login <other-host> when you already have valid credentials for it skips the browser and switches your active install to it (re-pointing auth hostname, token, broker, remote, and the shared incus current remote). Pass --force to re-authenticate anyway.

Tailnet precheck. Unless --skip-setup is given, login refuses to start the device flow on a machine that is not itself a Tailscale node (tailscale missing, logged out, or stopped): the v2 remote lives at the sidecar's tailnet IP and tenant machines sit behind its subnet route, so completing login would leave the tenant unreachable. Reference grammar (ADR-0020): [tenant@][[dns-suffix:]project:]machine. The colon count selects scope — 0 = current install + current project, 1 = current install + named project, 2 = named install (by its Tenant DNS Suffix) + project. A bare machine name is the current project's machine when it exists there; only otherwise is it looked up across projects (one hit resolves, several ask). A single colon is always project:machine (there is no silent incus-native remote:instance fallback). Naming another install switches to its incus remote (<suffix>, one per install; the named project is applied per-call) automatically; if you're not logged into that install, connect errors with sc login guidance rather than auto-provisioning. The same grammar is accepted by create, the machine-lifecycle commands, and image save. Messages print a machine's full path as tenant@remote:project:machine (thieso2@obelix:work:dev); the tenant@ prefix is accepted and ignored on input, so a printed path pastes back into any command.

connect starts a stopped machine before refreshing known hosts or handing off to SSH. It uses SSH to the machine's private IP and uses the private machine hostname as the host-key alias. Local DNS is useful for private URLs, but it is not required for Machine SSH Access.

If the machine is missing, connect asks before creating it — Machine thieso2@obelix:default:dev does not exist. Create it? [y/N] — so a mistyped name costs a re-run rather than a container. fix applies idempotent maintenance fixups to a running machine over SSH (as the login user, via sudo). Cloud-init only runs at a machine's first boot, so a machine built before a fixup shipped never receives it; fix backfills the change in place. It resolves the same [[remote:]project:]machine reference as connect (creating/starting the machine if needed — fix creates without prompting, unlike connect). --check reports status and changes nothing; --only <name> limits it to the named fixup(s).

Registered fixups:

  • agent-forwarding — bootstraps the machine into the /.sc shared-scripts model (ADR-0022). It installs the stable shims cloud-init bakes on fresh machines (/etc/ssh/sshrc plus appended blocks in /etc/zsh/zshrc and /etc/bash.bashrc, each sourcing /.sc/platform/… then /.sc/local/…, [ -r … ]-guarded) and converges the project's shared /.sc/platform payload — which carries the forwarded-SSH-agent republish/consume logic — over the Incus API, once per project. Script bodies are no longer pushed per machine; a later platform-script change reaches every machine centrally. It also reports (never rewrites) a broken hand-rolled ~/.zshrc that republishes through the consumed path.
  • ssh-key — enrols the current CLI SSH key through the restricted Incus API before any SSH connection is attempted. Use it when a Machine was created from a stale project-profile key and sc connect cannot authenticate; it is scoped to the named Machine, so local-home Machines are repaired independently. It is strictly additive: no line of authorized_keys is ever removed or replaced — a hand-added key stays, an older CLI key stays — the current key is only appended when it is missing (inside the Sandcastle marker block, so an allowlist revoke can still drop every Sandcastle-managed key). Afterwards it prints every enrolled key as an ssh-keygen -l line, marking the current CLI key. It also maintains a marker-delimited Host block for the machine at the top of the local ~/.ssh/config (<machine>.<project>.<suffix>, its public hostnames and its private IP → User, IdentityFile = the CLI key, IdentitiesOnly yes, HostKeyAlias = the private hostname), so a bare ssh <fqdn> or ssh <ip> logs in exactly like sc connect instead of offering ~/.ssh/id_* and falling back to a password prompt. Only the block between its own markers is ever rewritten; --check reports ~/.ssh/config: current or NEEDS FIX.
  • sudo — restores the login user's passwordless sudo over the Incus API, as root: membership in group sudo and the <user> ALL=(ALL) NOPASSWD:ALL rule cloud-init writes to /etc/sudoers.d/90-cloud-init-users at first boot (appended if the file exists, visudo -checked before it is moved into place), then proves it with sudo -n true as that user. Every other fixup runs sudo sh -s over SSH and so cannot repair this itself; a sudo-rs machine (Ubuntu 25.10+) that lost the rule answers sudo: I'm sorry <user>. I'm afraid I can't do that — that is "no sudoers rule", not a wrong password. Runs before the SSH fixups; --check prints sudo: OK or NEEDS FIX (…).
  • caddy-publications — refreshes the Machine Caddy setup and readiness marker. It never creates or retargets DNS and never obtains certificates itself; it restores the Machine-side contract so the Auth App can deliver an already-issued Machine Public Hostname certificate and reload Caddy on :443.
  • cloudflared — repoints an already-installed Machine Tunnel connector to /.sc/platform/sbin/cloudflared and restarts it when its token file and service unit are present. It never creates a tunnel or obtains a new token; use sc tunnel publish or republish if those resources are absent.

Without a terminal an ambiguous bare name is an error listing the candidates, never a guess — qualify it as project:machine.

Wildcards. Every part of the reference accepts shell-style globs (*, ?, [abc]), so one lifecycle command can act on a set. Quote the pattern so your shell does not expand it first:

sc stop 'gbrain:*'          # every machine in project gbrain
sc delete 'gbrain:*' --yes   # …and the confirmation names them all
sc restart '*:web-*'        # the web-* machines of every project
sc start 'g*:d*'            # d* machines in every project matching g*
sc stop '*:*:dev'          # the dev machine of every ENROLLED INSTALL
sc stop 'o*:gbrain:*'      # project gbrain on every install matching o*

A wildcard matches only machines that already exist, and one that matches nothing is an error. The machines are acted on concurrently and each is reported on its own line; a failure on one does not stop the others, and the command exits non-zero naming how many failed. The JSON payload keeps its historical {action, tenant, project, machine} shape when the reference names one machine literally, and becomes {action, tenant, selector, results[]} when it globs — with a remote on each result when the run spanned installs.

Globbing installs needs all three parts spelled out — '*:*:dev', not '*:dev'. A two-part reference stays project:machine unless its leading part exactly names an enrolled remote, so that 'g*:d*' filters projects and machines rather than changing meaning the day you enroll an install called gizmo. An install pattern matches the names sc remote list shows, so * never wanders into system incus remotes like images:.

Installs are swept one at a time (the reference's install picks which restricted certificate is in play, and only one can be active at a time), and installs legitimately have different project sets — '*:web:api' skips an install with no web project rather than failing, though a project no install has is still reported as the typo it is. If an install cannot be reached, a lifecycle command refuses the whole run rather than acting on a partial sweep; sc ls does the opposite and warns while showing what it did find.

Commands that act on exactly one machine — connect, fix, route publish, image save — accept a wildcard as a way to select that machine: it must narrow to one, otherwise they ask which (interactively) or error listing the candidates, qualified by install where the candidates span more than one.

A Sandcastle Path is the slash form of a reference, /remote/tenant/project/machine. It is a second grammar beside [[remote:]project:]machine, selected purely by shape: an argument that starts with /, ./, ../ or ~, or is exactly ., .., ~ or -, is a path; everything else is the colon grammar, unchanged. Relative paths resolve against the Current Position, the remote, tenant and project recorded in the nearest .sandcastle — the same file sc remote switch, sc tenant switch and sc project switch write, so the position is per directory tree and the switch commands keep working. sc cd composes those three switches in tree order (remote, then tenant — a Shared Tenant is entered through the Auth App exactly as sc tenant switch does — then project) and additionally records the level (level: tenant|remote|root) when the position stands above a project, plus the previous position for sc cd -. A remote that is not enrolled is an error with the enroll guidance; cd never enrolls. A path that pairs a remote with a tenant it does not serve (/obelix/moyn-dev when moyn-dev is enrolled as its own remote) is refused and names the paths that work (/moyn-dev/moyn-dev), or sc tenant switch when none is enrolled yet. A machine is a leaf: sc cd into one fails and points at sc connect.

Standing above a project. After sc cd .. the project is unset: creating commands (sc create dev, sc mkdir dev) refuse a bare name with not in a project, while reading and acting commands (sc connect dev, sc stop dev) resolve it with the tenant-wide unique search that already serves bare names, and sc ls lists the children of the position (projects under a tenant, under a remote the one tenant it is enrolled for — two remotes of the same install for different tenants each show their own, and the same tenant name on two installs appears under both remotes — remotes under /) and reads every bare argument as a child. Every segment of a path may be a shell glob, matched level by level against the tree (sc ls '/*/*/*/dev' is sc ls -a '*:*:dev'), and ** matches across levels: in a listing it stands for zero or more directories (sc ls -d '../**' is every project and machine of the tenant, sc ls '/**/web/*' the machines of every project called web anywhere), in a machine reference for as many * as reach a machine (sc stop '/**/dev' is sc stop '*:*:dev', sc ls '/obelix/acme/web/**' every machine of that project). An unreadable install under ** is a warning: line, not a failure. A ** inside a longer segment (web**) is a plain *. Text output follows ls: matched machines are files — they print first, together, one path per line (with -l one table whose MACHINE column holds the path); every matched directory then prints its path on a line of its own followed by its children, blocks separated by a blank line, so a single match still says what it is; -d prints the matching paths, -l a table whose columns depend on the level (REMOTE TENANT PROJECT AUTH, TENANT ROLE PERSONAL, PROJECT DOMAIN IMAGE, MACHINE TYPE STATE IP CREATED), -R recurses down to machines. A directory that cannot be read inside a larger listing becomes a warning: line. JSON is {listings: [{path, level, entries: [{name, kind, fields}]}], warnings}. Data comes from the sources the plain commands use: the local incus config for remotes, the Auth App for tenants, the Auth App resource cache (live Incus fallback) for projects and machines.

Cache-backed listing. When the admin server has its event-bus resource cache enabled (a server-side config toggle, SANDCASTLE_RESOURCE_CACHE on the auth-app serve process — on by default) and that cache has finished its initial sync, sc ls answers from it instead of issuing a live per-project Incus query for every project — the same filters, wildcards, and -a apply, just against an in-memory index kept current from Incus events rather than polled fresh each time. This is what turns a several-second sc ls -a against many projects into a near-instant one. If the cache toggle is off, the admin server just started and hasn't finished its initial read yet, or its event-bus connection has dropped, sc ls transparently falls back to the live per-project query — same behavior as before this cache existed, with no error shown. Run with VERBOSE=1 to see which path was used and why a fallback happened. The request asks the admin server only for the resource types the command is going to print — machines, plus one per --networks/--storage-pools/--storage-volumes/--profiles/--images flag — so a plain sc ls does not pay to transfer sections it would discard. The round trip is given 5 seconds before falling back; on a slow link (a tunnelled Auth Hostname where the TLS handshake alone can cost seconds) set SANDCASTLE_LS_CACHE_TIMEOUT to a longer Go duration such as 10s — falling back is usually the slower outcome, since the live path re-queries every project. One resource type degrades rather than blocking: if a storage pool's volumes cannot be listed — typically one instance whose backing dataset is gone, which fails the listing for every project on the host — that pool is skipped with a warning in the auth-app log and the cache still serves everything else, so only sc ls --storage-volumes is affected.

Other resource types (cache-backed only). sc ls --networks, --storage-pools, --storage-volumes, --profiles, and --images each add a section listing that resource type, scoped the same way the machine listing is. These sections are populated only when the cache-backed endpoint answers the request — the live per-project path never fetched these resource types, so on a live-path fallback the flags are silent no-ops and sc ls shows machines only, exactly as it always has.

Machine Tunnels

Dedicated Cloudflare connectors. A Machine Tunnel is opt-in and distinct from both a Machine Public Hostname and a Public Route. A Machine can carry several tunnels: each hostname gets its own Cloudflare Tunnel, run token, and namespaced cloudflared systemd connector, so different hostnames may target different local ports. The unit always starts /.sc/platform/sbin/cloudflared, the centrally versioned platform launcher; it caches the provider executable locally only for execution. No public IP or inbound host port is needed. The Auth App uses the encrypted token already registered for the matching Public DNS Zone and returns only that tunnel's run token to the Machine. The account API token is never placed in the Machine or supplied to this command.
sc tunnel publish wordpress:dev --port 3000 --hostname app.example.com
sc tunnel unpublish wordpress:dev --hostname app.example.com
sc tunnel unpublish wordpress:dev
sc tunnel unpublish wordpress:dev --hostname 'app-*.example.com'

Before publishing, an administrator registers the hostname's Public DNS Zone with a Cloudflare token holding account-level Cloudflare Tunnel: Edit, plus DNS: Edit and Zone: Read on that zone. Repeating the same command is safe: Sandcastle reuses its matching tunnel CNAME. It refuses a DNS record with another target. Cloudflare ownership is recorded on the Machine before its connector starts; if that installation fails, sc ls shows (pending) and repeating the same publish resumes it. Existing connectors created by an older CLI can be repointed to the shared launcher with sc fix <machine> --only cloudflared after sc payload-sync. sc tunnel unpublish removes its matching CNAME and dedicated connector, clears that publication metadata, is safe to repeat, and never removes another DNS record. Omit --hostname to remove all tunnels recorded on that Machine; a shell-quoted wildcard selects only matching recorded hostnames. It never scans or removes unrelated DNS names. Wait for DNS propagation before reusing a hostname. Do not reuse a Machine Public Hostname: release it first with sc hostname remove, because that feature deliberately owns a direct private-address DNS record while a tunnel owns a proxied Cloudflare CNAME.

Tailnet HTTPS publication

For tunnel DNS diagnostics, query public A/AAAA records or inspect the proxied CNAME in Cloudflare's dashboard/API; the public resolver returns edge addresses.

One certificate for an authorized wildcard route. The compatible default is one broker-authorized certificate per concrete hostname, issued on its first request. When something else already owns the host's :80/:443. Use --route-ingress acme-proxied instead of acme. Because the certificate is issued inside the appliance, the front must not terminate TLS for route hostnames.

The front runs Caddy built with caddy-l4 (xcaddy build --with github.com/mholt/caddy-l4) as a listener wrapper, so it still binds :80/:443 itself and its own sites keep their normal certificates and redirects — only matching connections are spliced away:

{
	servers :443 {
		listener_wrappers {
			layer4 {
				# one file per sandcastle install, generated by its Auth App
				import /etc/caddy/sandcastle/*.caddy
			}
			tls
		}
	}
}

# :80 for anything this front does not serve itself — HTTP-01 challenges and
# the appliance's own https redirect
http:// {
	reverse_proxy <appliance-ip>:80
}

The SNI list is never hand-maintained. Deploy the appliance with --route-front <project>/<instance> (e.g. infrastructure/sc-edge) and the Auth App writes /etc/caddy/sandcastle/<prefix>.caddy into that instance over the Incus admin socket it already holds, then reloads the front — on every publish, delete, and reconcile pass. One file per install, so several sandcastles share one front without colliding, and publishing a custom hostname needs no operator action. A front that is briefly unreachable never fails a tenant's publish: the route serves locally and the next reconcile re-delivers.

Public DNS Zones admin

A Public DNS Zone is a Cloudflare-hosted name (e.g. hase.de) an admin registers with the install together with an API token that lets the Auth App manage records in it (ADR-0027). It may be the Cloudflare zone itself or any name inside one (e2e.sc.tc42.uk inside the Cloudflare zone tc42.uk): the Cloudflare zone that contains it is resolved at add time and shown by list, and every record is written into that Cloudflare zone under its full name. Tenants then claim Project Domains under it (baum.hase.de), and every Machine created in such a project gets a Machine Public Hostname (web.baum.hase.de) with a Let's Encrypt certificate issued centrally over DNS-01. This section covers the zone registry (admin) and Project Domain claims (tenant); Machine Public Hostnames and certificates arrive with the following slices.

Both roots. The registry lives behind the admin-only /api/public-dns-zones endpoint of the Auth App, so the command works through a tunnel and needs no appliance restart or redeploy. It is available as sc-adm public-dns-zone … and, identically, as sc admin public-dns-zone …. It uses the CLI Auth Token from sc login; the logged-in user must be a Sandcastle Admin.

Register, list, rotate, remove

sc-adm public-dns-zone add hase.de --token-file ~/.cf-hase-token   # validates against Cloudflare, stores the token encrypted
sc-adm public-dns-zone add hase.de --token <token>               # token on the command line (ends up in shell history)
pass show cf/hase.de | sc-adm public-dns-zone add hase.de          # token on stdin
sc-adm public-dns-zone add e2e.sc.tc42.uk --token-file ~/.cf-tc42    # a name inside the Cloudflare zone tc42.uk; the token is scoped to tc42.uk
sc-adm public-dns-zone list                                          # ZONE  CLOUDFLARE-ZONE  CLOUDFLARE-ID  TOKEN  CLAIMS  CREATED-BY  CREATED
sc-adm public-dns-zone list --output json
sc-adm public-dns-zone set-token hase.de --token-file ~/.cf-new  # rotate in place, same validation
sc-adm public-dns-zone remove hase.de                              # refused while any Project Domain is claimed under it
sc-adm public-dns-zone add hase.de --token-file … --dry-run       # every mutating verb takes --dry-run
  • Token scope (Cloudflare → My Profile → API Tokens → Create Token, custom): Zone > DNS > Edit plus Zone > Zone > Read, restricted to the Cloudflare zone that contains the Public DNS Zone. Zone Read is used only at add/set-token to resolve that zone; runtime needs DNS Edit. Cloudflare tokens cannot be scoped below zone level — register a name inside the zone (sc.tc42.uk) to keep Sandcastle's records apart, but the token can still edit the whole Cloudflare zone.
  • Validation. add and set-token call Cloudflare with the token: the zones the token can read are listed (GET /zones, paged) and the one whose name equals the Public DNS Zone or is its parent on a label boundary — the longest such match — is chosen; then a one-record DNS listing against it proves DNS access. Nothing matching prints Cloudflare rejected the token for zone <zone>: the token cannot see a zone containing <zone> (check Zone > Zone > Read and the zone the token is scoped to); any other failure prints Cloudflare rejected the token for zone <zone>: <api message>. A rejection stores nothing. If the Auth App cannot reach Cloudflare at all, that is reported as such, not as a rejection. The resolved Cloudflare zone is stored next to its id, printed by add/set-token ((inside Cloudflare zone tc42.uk, id …)) and listed as CLOUDFLARE-ZONE (cloudflareZone in JSON).
  • Normalization. Zones are lowercased, trimmed, and stripped of a trailing dot; a zone needs at least two labels.
  • No nesting. add hase.de when sc.hase.de is registered (or vice versa) is refused: public DNS zone <zone> overlaps registered zone <other>; zones may not nest. A re-add of an existing zone says public DNS zone <zone> is already registered (use set-token to rotate its token).
  • Remove has no --force. While Project Domains are claimed under the zone it prints public DNS zone <zone> still has claimed project domains: <d1> (<tenant>/<project>), …; unset them first.
  • At rest. The token is AES-GCM encrypted in the Auth Database under a deployment key (public_dns_zone_key in auth_app_meta, generated on first use). It is never logged and never returned by any endpoint; list shows the first 8 hex characters of its SHA-256 as TOKEN so you can tell tokens apart.

Project Domains user

A tenant claims a Project Domain for one of its projects: a name at least one label below a registered zone (baum.hase.de under hase.de). The claim is an install-wide reservation in the Auth Database (project_domain_claims) and, once committed, is stamped onto the Incus project as user.sandcastle.v2.domain and rendered into the project's default profile: machines created from then on seed the derived <machine>.<domain> into the PUBLIC_HOSTNAMES= line of /etc/sandcastle/machine.env — their identity (fqdn:, FQDN=) stays the Machine Private Hostname (ADR-0028 retired the per-machine Naming Mode; a machine's public names are a set). Machines created earlier are re-derived by the zone reconciler within a minute (list key, A records, certificate, hostnames file) — set-domain/unset-domain are allowed with machines in the project.

sc project create zp --domain baum.hase.de            # claim + create in one request (claim first; the row is dropped if Incus fails)
sc project set-domain zp baum.hase.de               # claim for an existing project, or replace its domain
sc project unset-domain zp                            # release the domain; new machines are private again
sc project status zp                                  # Domain: baum.hase.de   (zone hase.de) + the per-machine table
sc project delete zp --yes                            # releases the claim, then deletes the Incus project
sc project set-domain zp baum.hase.de --dry-run     # every mutating verb takes --dry-run
  • Shape. Lowercased, trimmed, trailing dot stripped; ASCII labels only (no IDN); labels may not start with _ or *. The zone is the unique longest registered suffix; none → no Public DNS Zone covers <domain> — ask your admin. The zone apex itself cannot be claimed (project domain "<d>" is a zone apex; claim at least one label below <zone>) — a one-project zone is expressed by registering that name as the zone. *.<63-char machine>.<domain> must fit in 253 characters, so a domain is at most 187 characters (project domain "<d>" is too long: …).
  • Conflicts block regardless of tenant: an identical claim, a claim above or below the candidate, an existing Public Route hostname equal to or inside it (a leading *. is stripped first), and the install's own names (the Auth Hostname and the route base domain, or anything above them). Cross-tenant overlaps never name the owner: project domain "<d>" overlaps a domain already claimed on this install; choose another. An overlap with another project of your own tenant does: project domain "<d>" overlaps "<existing>" claimed by project "<p>" in this tenant. Routes and install names print project domain "<d>" is reserved by this install. The scan and the insert run in one BEGIN IMMEDIATE transaction, so two racing claims are serialized; the reverse rule holds too — sc route publish with a custom hostname inside a claimed domain is refused with route hostname "<h>" is inside project domain "<d>" claimed on this install.
  • Re-claim and change. Claiming the domain a project already holds is a no-op (exit 0, project domain "<d>" already claimed by this project). set-domain with a different domain replaces the claim. Both set-domain and unset-domain are allowed with machines in the project (ADR-0028 slice 3 retired the former "has machines with a public name" refusal): the zone reconciler re-derives every machine's <machine>.<domain> on its next pass — the list key, A records, delivery of the shared project certificate, and the hostnames file — and explicit hostnames are untouched.
  • Release. unset-domain and project delete release the claim immediately; the domain is re-claimable at once (Let's Encrypt's 5-certificates-per-identifier-set weekly limit still applies to a name that was already issued for). A project deleted out-of-band (sc-adm project delete, incus project delete) leaves an orphan row that the Auth App's 5-minute reconcile loop drops; an Incus project carrying user.sandcastle.v2.domain without a claim row is logged once and ignored — never auto-claimed — until its tenant runs set-domain (claims it) or unset-domain (clears the key).
  • Only through the Auth App. The verbs use POST /api/projects (domain), PUT/DELETE /api/projects/<name>/domain and DELETE /api/projects/<name> with the CLI Auth Token from sc login. The broker path (--broker, or no login) cannot claim: --domain is not available on this install. Error bodies are {"error": "…"} and the CLI prints them verbatim.

One certificate per Project Domain

set-domain orders one DNS-01 certificate for <domain> and *.<domain>, stored once at the Auth App and renewed using ARI. Creating, copying and deleting machines do not order certificates for derived names or one-label aliases. unset-domain drops the project certificate. Existing derived-name certificates expire without renewal or revocation.

sc project set-domain tod0s tod0s.tc42.uk --dry-run
sc project set-domain tod0s tod0s.tc42.uk
sc project status tod0s --json
sc create tod0s:x1 --alias admin-x1 --alias console-x1
# Public name: x1.tod0s.tc42.uk (A record pending, served by project certificate)
sc delete tod0s:x1 --dry-run

status, set-domain and unset-domain accept an omitted project, using the current project. Status includes certState, certNotAfter and sans. Machines carry cert-state=project and an empty cert-not-after; sc ls and its JSON output resolve the shared certificate's current state and expiry. Machines with additional per-name certificates report the worst state and earliest expiry across their names.

Aliases and explicit hostnames

sc hostname add tod0s:x1 admin-x1.tod0s.tc42.uk --dry-run
sc hostname add tod0s:x1 admin-x1.tod0s.tc42.uk
sc hostname list tod0s:x1
sc hostname remove tod0s:x1 admin-x1.tod0s.tc42.uk
sc hostname add tod0s:x1 '*.x1.tod0s.tc42.uk'
sc create tod0s:web --hostname web12.tc42.uk --fqdn shop.tc42.uk

--alias is repeatable and accepts one DNS label under the machine's own Project Domain. Aliases are explicit hostname reservations, removable per machine. The derived name remains non-removable. Derived names and one-label aliases use the project certificate and order nothing; deeper names, names outside the domain, and Public DNS Zone apex names use per-name orders. An explicit wildcard orders that wildcard alone. Names remain subject to zone coverage and reservation conflicts; another project's domain cannot be used.

Hostname flags are claimed before machine creation, with compensation if creation fails. --hostname and --fqdn keep the same meaning outside the Project Domain. Every affected mutation supports --dry-run and shows its certificate decision.

DNS, certificate delivery and copies

The Auth App converges A records for derived names and their wildcards, plus explicit names. On instance-started and project renewal it checks every machine independently and pushes the certificate and key to /etc/sandcastle/tls/<domain>/. Failures retry without creating another order. ARI timing, encrypted key storage, order backoff and concurrency limits remain in use.

caddy-setup --refresh reads the authoritative hostname list and /etc/sandcastle/project-domain. Every exact one-label name uses the shared directory; explicit deeper/outside names keep their per-name directories. The project wildcard does not cover a wildcard beneath a machine; request that explicitly with sc hostname add. Private tenant-CA names and /etc/sandcastle/tls/cert.pem are unchanged.

A raw incus copy requires no user-key overrides: the reconciler derives the destination name, clears copied certificate metadata, and creates DNS records. Source aliases stay reserved to the source. Deletion removes machine A records and leaves no new certificate row for derived names or aliases; per-name certificates outside project coverage retain their existing retention policy. Unsetting a domain clears the shared-directory selector on running machines.

Upgrade the Auth App and shared platform payload along with the CLI. See the project certificate contract and the acceptance procedure in docs/e2e-sc2.md.

6. Tailscale — the Tenant Tailnet

How it works

Every sandcastle is part of a Tailscale tailnet by default — this is the main operation mode, not an optional add-on. Tenant creation brings the tenant's sidecar onto the Tenant Tailnet (unattended with --tailscale-authkey, or interactively via the printed login.tailscale.com URL), and all tenant access rides it: the restricted Incus remote lives at the sidecar's tailnet IP (the Incus Reach), machine SSH and tenant DNS travel over the sidecar's advertised subnet route, and sc login refuses a client that is not itself a tailnet node.

The sidecar sits on the tenant's private bridge at .2 (e.g. 10.248.0.2) and acts as a subnet router: it advertises the entire tenant private CIDR (e.g. 10.248.0.0/24) to your Tailnet. Any device on your Tailnet can then reach all machines in the tenant directly by their private IP, without needing Tailscale installed in each machine.

Tailscale admin console step: The advertised route must be approved in your Tailscale admin console — or zero-touch via an ACL autoApprovers rule on tag:sandcastle (see docs/e2e-sc2.md).

Re-attach Tailscale on a tenant (interactive)

Tenant creation already attaches the sidecar; use this to re-attach or repair a detached one. Starts tailscaled inside the sidecar and runs tailscale up --timeout=60s --advertise-routes=<tenant-cidr>. Without an auth key, Tailscale may print a browser auth URL; the command is still bounded by the timeout so unattended flows fail cleanly.

sandcastle tailscale up
sandcastle tailscale up acme  # explicit tenant

Activate with an auth key (unattended)

sandcastle tailscale up --auth-key tskey-auth-...

Generate auth keys in the Tailscale admin console. Use a reusable key if you need to re-run this after a container restart.

Check Tailscale status

sandcastle tailscale status

Reports the Tailscale state, Tailnet name, assigned IPs, and which routes are being advertised.

Detach Tailscale

Runs tailscale down inside the sidecar. The container keeps running; only the Tailnet attachment is removed.

sandcastle tailscale down

7. Auth App service admin

How shared infrastructure is deployed

The Auth App and the Sandcastle Broker run as appliances on the Incus host. Deploy them together with sc-adm install (see §3), or piecewise with sc-adm auth-app deploy and sc-adm bootstrap. This section documents how the running Auth App behaves once deployed.

The Auth App runs sandcastle-admin auth-app serve with a persistent SQLite database at /var/lib/sandcastle/auth/auth.db. When an Auth Hostname is configured, the appliance's ingress routes it to the Auth App. CLI Device Login provisions Personal Tenants only after browser approval, not at allowlist add time or browser-only GitHub login time. During CLI Device Login, the user CLI sends the local OS username and the Personal Tenant stores it as the Unix user for future Machines. --username and SANDCASTLE_AUTH_DEFAULT_UNIX_USER are fallback defaults for clients that do not send a local Unix username.

Verbose logging & the Activity Log. The Auth App and the broker write a verbose, timestamped line for every HTTP request and every unit of work (named "spans" such as provision.personal_tenant, project.create, issue workload token), each with its duration, to stderr — visible with journalctl -u sandcastle-auth-app / journalctl -u sandcastle-broker. The Auth App additionally persists its entries to the logs table in auth.db and exposes them at / → Activity log (https://<auth-hostname>/logs). Visibility is scoped by identity: a Sandcastle Admin sees every user's entries (plus system entries with no user), while every other signed-in user sees only her own. The page supports a free-text filter (?q=) over event/path/detail and a row cap (?limit=, default 500). Log rows are retained indefinitely (no automatic pruning). Broker activity currently appears only in the broker's own journald stream, not in the Activity Log.

Initial Sandcastle Admins from SANDCASTLE_AUTH_ADMIN_GITHUB_USERS can sign in through GitHub and manage the Login Allowlist at /admin/allowlist and Tenant Access at /admin/access. The allowlist accepts explicit GitHub users only; password login is not available. For disposable lab integrations, SANDCASTLE_AUTH_DEBUG_DEVICE_USER enables POST /debug/device/approve to approve CLI Device Login as that allowlisted user without a browser session. SANDCASTLE_AUTH_TAILSCALE_AUTHKEY can be set at deployment to return a Tailscale auth key to approved CLI Device Login clients for unattended tenant sidecar attachment; this is intended for disposable integration environments and is not stored in Incus metadata.

The Auth App also serves per-tenant OIDC provider metadata at /t/<tenant>/.well-known/openid-configuration and per-tenant public signing keys at /t/<tenant>/.well-known/jwks.json. Legacy global metadata remains available at /.well-known/openid-configuration and /.well-known/jwks.json. Private signing keys are stored encrypted in the Auth Database. See Sandcastle OIDC Configuration for the full provider and machine token flow.

Users can manage User-owned, tenant-scoped Cloud Identity Configs at /cloud-identities. Use sc cloud-identity gcp setup --tenant <tenant> after sc login to configure tenant-scoped GCP Workload Identity Federation, save the Auth App config named gcp for that tenant, and print the audience and service account impersonation URL for confirmation. Set a project default with sc project set-cloud-identity default gcp; project defaults are accepted only when the named config exists for the current tenant.

Serve the Auth App

sandcastle-admin auth-app serve \
  --listen :9444 \
  --database /var/lib/sandcastle/auth/auth.db \
  --auth-hostname auth.example.com \
  --github-client-id ... \
  --github-client-secret ... \
  --admin-github-users octocat,hubot \
  --debug-device-user octocat \
  --simulate-github-token <shared-secret> \
  --acme-directory https://acme-staging-v02.api.letsencrypt.org/directory

Machine Certificates (--acme-directory). An install-level setting (also on sc-adm install / sc-adm auth-app deploy, stored on the appliance like --acme-email): the ACME directory the Auth App orders Let's Encrypt certificates from for every Machine Public Hostname — the derived <machine>.<Project Domain> and every explicit hostname (Public DNS Zones, ADR-0027/0028). Default is Let's Encrypt production (https://acme-v02.api.letsencrypt.org/directory); pass the staging URL above for e2e and first live runs so no production budget is spent. The ACME account is one per install per directory, with --acme-email as its contact, created on the first order. Staging and production certificates never mix: switching the setting re-orders every certificate. sc create in a project with a Project Domain calls POST /api/machine-certificates for the derived name after the machine exists (5 s timeout, never failing the create; an explicit --hostname gets its row with the claim, before the instance exists) and prints Public name: … (A record pending, certificate pending — see: sc project status <project>); if the Auth App is unreachable or the zone's Let's Encrypt budget (50 certificates per registered domain per 7 days) is spent, the parenthesis says so and the reconciler retries.

The debug device user flag is intended only for disposable integration environments. It registers POST /debug/device/approve, which approves a pending device code as the configured allowlisted user. Use --tailscale-auth-key only for unattended lab login flows where approved CLI clients should receive a Tailscale auth key for tenant sidecar attachment.

Simulated GitHub mode (dev/e2e only). Passing --simulate-github-token <secret> (also accepted by auth-app deploy; env SANDCASTLE_AUTH_SIMULATE_GITHUB_TOKEN) lets the Auth App fabricate GitHub logins with no real OAuth app — --github-client-id/--github-client-secret become optional. It registers GET/POST /oauth/github/simulate, which (gated by a constant-time comparison against the shared secret) allowlists the given username, mints the browser session, and optionally approves a pending device user_code. Drive it from the CLI with sc login <auth-host> --simulate-token <secret> --as <username>. Never enable in production — anyone holding the token can authenticate as any user. A wrong token returns 403; an unset token leaves the route unregistered (404).

Update the deployment (sc-adm update)

Updates this install's global components — the auth-app and broker appliances — from a GitHub release: it downloads the matching linux-<arch> asset per appliance, verifies it against checksums.txt, pushes it into each appliance, restarts the service, and stamps user.sandcastle.binary-version into the instance config. Idempotent — re-run to repair a partial update. Components are scoped by the installation prefix, so a neighbour install sharing the host is untouched. The image-builder appliance carries no sandcastle binary and is not updated.

One Incus remote can host several installs, so the command must know which one to act on. It resolves the install from --prefix, else an explicit SANDCASTLE_INCUS_PROJECT_PREFIX, else the install the sc CLI is currently on (the one sc ls lists), else auto-detection: with a single install on the remote it is picked automatically (and named on stderr); with several it refuses and lists them so you pass --prefix. Each case names its choice on stderr — targeting install "obelix" (the one `sc ls` is on).

Which Incus remote it talks to. Admin commands follow the same deployment the user CLI is on, so sc admin update never updates a different sandcastle than sc ls lists. The admin remote is resolved from SANDCASTLE_ADMIN_REMOTE/admin_remote or an explicit SANDCASTLE_REMOTE first — an explicit choice always wins — then by matching the user remote's server certificate or address, then by asking each enrolled admin remote which installs it hosts (the remote carrying <install>-infra). That last step is what makes a v2 install resolvable at all: a user remote points at the tenant sidecar on the tailnet (ADR-0017), not at the Incus host, so its cert and address never match the admin remote's. Only if every step fails does it fall back to the global incus default remote, and it says so with a warning naming the install — that fallback can be a different deployment entirely, so set SANDCASTLE_REMOTE when you see it.

sc-adm update --check                 # fleet version table from the stamps (works for stopped instances)
sc-adm update                         # update auth-app + broker to the latest release
sc-adm update --prefix idefix         # target a specific install when several share the remote
sc-adm update --version v0.3.1        # pin (an older tag rolls back)
sc-adm update --tenants alice,bob     # also force-roll these tenants' sidecars
sc-adm update --all-tenants           # force-roll every tenant sidecar (e.g. a security fix)

Tenant sidecars are normally tenant-managed: each tenant runs sc update, which the deployment serves by pushing its own running binary — so sidecars can never run ahead of the deployment. --tenants/--all-tenants is the operator override for security fixes and abandoned tenants. Appliances with no version stamp (deployed before the update system) show unknown and are treated as outdated; their first update self-heals the stamp. The auth-app also shows an always-visible version card on its web pages: green when current, amber with the sc-adm update command and a release-notes link when behind.

Version skew. The CLI sends its version on every auth-app/broker call and responses carry the appliance version: a mismatch prints a one-line warning, never a block. A known-breaking release can set a minimum CLI version, in which case older CLIs get a clean “run sc update” refusal instead of protocol errors.

Manage the Login Allowlist

Adding a user verifies the GitHub username and stores the normalized username plus GitHub numeric account ID. Image Builder appliance (build in a container, publish to GHCR)

Instead of building locally with docker, the Image Builder builds Sandcastle Images inside a dedicated, admin-managed Incus container and publishes them to GHCR. It is an infrastructure appliance, not a Machine. See docs/adr/0010-image-builder-appliance.md.

export SANDCASTLE_REMOTE=big
export SANDCASTLE_GHCR_TOKEN=<github PAT with write:packages>
mise run image:all:build-remote          # or sc-adm image build-remote base|ai|dev|all

How it works: the sc-build project holds a persistent sc-builder container (neutral images:debian/13, security.nesting, /dev/fuse) that builds with rootless podman against a cache volume. build-remote ensures the appliance and a one-time ghcr OCI remote, ships the working-tree build context in, logs in with the token over stdin (never persisted), builds :latest + an immutable :<git-describe> tag, pushes to GHCR, then copies the immutable tag into the local Incus alias and syncs tenant aliases. The AI image is built FROM the immutable base tag of the same run; the dev image is built independently FROM ubuntu:26.04 (a different OS lineage from base/AI's Debian), so it does not chain off the base build.

Provisioning is decoupled from building. On a cold start (no appliance) build-remote auto-provisions; on a warm appliance it only starts it and builds, skipping the (idempotent) provision step for speed. Provision deliberately with mise run image:builder:provision (or sandcastle-admin image builder provision) — e.g. after changing the provision toolchain. Builds are heavily cached: the Dockerfiles use RUN --mount=type=cache for apt/npm and the build runs with BUILDAH_LAYERS=true, so a no-op rebuild is seconds. Pass VERBOSE=1 to stream the underlying podman build/push output live.

Flags: --require-clean (refuse a dirty tree), --no-push, --no-import, --rebuild-builder, --ghcr-repo, --ghcr-user, --remote, --platform, --dry-run. Manage the appliance with sandcastle-admin image builder provision, sandcastle-admin image builder status, and sandcastle-admin image builder destroy [--yes] [--keep-cache] (prompts for confirmation when run interactively). GHCR packages must be public-read so the Incus host pulls without credentials; the token is only used to push.

Normal sc user commands ignore local .env and read only saved Sandcastle config plus explicitly exported environment variables.
